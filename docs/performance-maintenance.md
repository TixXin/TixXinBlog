# 性能验证与有限优化

本页记录已实施、可以复核的局部改进。原始计时、SQL、执行计划和截图只保留在本机 `.artifacts/`，不随 Git 分发。这里的服务方法计时不能当作生产 HTTP、页面首屏或吞吐承诺。

## 公开文章列表只取列表字段

`PostService.findMany` 原先在加载标签时默认选择 `post.*`。`toPostItem` 实际只使用列表资料，数据库却同时返回原始 Markdown、解析正文、SEO 配置和关联数组。多标签联表会重复传回同一篇正文。对于普通列表，12 篇、每篇 2 个标签产生 24 行；含标签搜索条件的当前 ORM 查询产生 48 行。

本轮只为公开列表指定 `fields`：编号、slug、标题、摘要、封面、类别、阅读分钟、互动计数、发布日期、专栏、置顶及标签名称/颜色。标签编号由 ORM 为关联装配补入。映射函数的参数类型同样收窄为这些实际依赖。没有改变 WHERE、排序、分页、正文搜索、公开过滤、文章详情或结构化关联逻辑，也没有引入索引或缓存服务。

### 方法和样本

工具：`src/backend/server-main/tests/post-list-performance.ts`。

- 使用现有隔离工厂创建临时 PostgreSQL 数据库、媒体目录、备份目录与博主账号，使用真实受管封面。保留工厂 106 篇文章，另外写入 30 篇公开长文和草稿、归档、软删除各 1 篇；合计 139 篇、136 篇公开。
- 每篇长文 Markdown 为 102,555 UTF-8 字节，解析正文 JSON 约 143 KB，包含中文标题、段落、代码、表格和图片。长文各有 2 个标签，受测列表前两页全部是长文。不是删减内容后得出的结果。
- 使用 Node 24.16.0、PostgreSQL 16.14，通过 `tsx` 运行源代码 `PostService`，现有编译目录仅用于隔离工厂。没有运行 `nest build` 或清理共享 `dist`。
- 修改前先运行一次真实旧实现并捕获其 SQL。配对对比在同一个隔离库中进行：当前服务为优化组；对照组仅从同一次 `findAndCount` 配置移除 `fields`，恢复旧投影，保留其他查询和序列化代码。
- 每次创建新的 ORM fork，避免一级缓存掩盖数据库读取；每组预热 3 次，再按先后顺序交替执行 20 对请求。未清数据库/操作系统缓存，不能称为冷缓存。同机其他构建负载没有被隔离，因此同时报告范围。
- 捕获 ORM 实际 SQL 和参数，以同一 SQL 运行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。驱动返回对象的 JSON 字节数在独立采样中测量，字节统计的序列化开销不混入计时样本。

### 配对实测

下表采用 2026-09-11 08:44 UTC 的完成采样。单位为毫秒；括号内是最小–最大值，各组各 20 次。

| 查询                     | 旧完整投影：服务方法中位数 | 新列表投影：服务方法中位数 | 旧/新 ORM 中位数 | 业务 JSON 字节，前后一致 |
| ------------------------ | -------------------------: | -------------------------: | ---------------: | -----------------------: |
| 第 1 页，每页 12 篇      |       36.05（32.56–46.12） |          4.30（3.91–7.76） |     36.01 / 4.27 |                    5,044 |
| 中文正文搜索，每页 12 篇 |     105.24（98.10–114.49） |       41.28（39.08–44.34） |   105.20 / 41.24 |                    5,043 |
| 第 2 页，每页 12 篇      |       37.41（33.06–45.66） |          4.32（3.83–4.91） |     37.37 / 4.29 |                    5,050 |

| 查询         | 旧驱动返回对象 JSON 字节 | 新驱动返回对象 JSON 字节 |
| ------------ | -----------------------: | -----------------------: |
| 第 1 页      |                5,834,932 |                    9,736 |
| 中文正文搜索 |               11,669,847 |                   19,455 |
| 第 2 页      |                5,834,944 |                    9,748 |

驱动对象 JSON 体积约减少 99.83%。这衡量返回行对象的内容量，**不是 PostgreSQL 协议线上字节数，也不是 HTTP 流量**。最终业务 JSON 原本已经不含全文，所有配对样本的完整响应内容、编号顺序、计数与 SHA-256 均一致。

DTO 映射中位数约 0.020–0.033 ms，最终业务 JSON 序列化约 0.015–0.017 ms，量级很小，没有把这部分波动计作主要收益。主要差异发生在取回、解析和 ORM 装配原本无用的长正文阶段。

执行计划也说明了边界：普通列表数据查询的规划行宽从 621 降为 208，执行时间单次观测为 0.333 / 0.294 ms，shared hit 均为 45、shared read 均为 0。正文搜索数据查询单次执行为 34.425 / 36.115 ms，shared hit 均为 650、shared read 均为 0；搜索仍需要读取正文进行匹配，COUNT 查询也没有消失。`EXPLAIN` 不把结果行传回应用，不能用它的执行时间替代驱动取回与 ORM 耗时。本轮没有声称改善正文搜索算法或数据库扫描范围。

### 正确性和复核

采样工具同时断言：三种主要查询的完整业务 payload 不变；中文正文独有关键词及 `%`、`_` 的字面检索仍然有效；类别、标签、置顶、专栏、升降序组合不变；30 篇长文跨 3 页无重复、无遗漏；撤回一篇后正文匹配从 30 减为 29，再公开恢复为 30。草稿、归档、软删除记录始终不进入公开结果。体积检查不使用易波动的耗时阈值。

## 先前开发环境基线的用途

原始索引是本机 `.artifacts/sustainable-blog/baseline/summary.md`，其指向：

- `browser-before/results.json`：1440×1000 Chromium、开发 Vite 服务、无 CPU/网络节流；首页、现有最长文章、图库和搜索。
- `api-before-partial/results.json`：日常公开 API 的有限只读采样；运行末尾发生实际 `ECONNREFUSED`，不能当作完整验收。
- `run-before/results.json`：首次内容盘点；`run-before-paced`、`run-before-stable` 等保留当时尝试；触发 429、热重启或失败的尝试没有合并为成功结果。
- `sql-analysis-plan.md`：当时尚未执行的方案；本页上方的隔离长文结果才是已执行证据。

当时日常库有 66 篇公开文章，所谓“最长文章”只有 3,922 字符分块 JSON、8 个标题，`contentRaw` 为空，不能代表真正长文。浏览器路由拦截阻止 `/view` 写入并禁用了 HTTP 缓存；“重复上下文”组包含该上下文的首次导航，不是纯热缓存。该基线没有移动端、Firefox/WebKit 或生产压缩产物数据，外链图片无 Timing-Allow-Origin 时传输字节还可能记为 0。

这些数字用于确定优化方向，没有与本次隔离长文服务方法计时相减，也没有写成线上提升。首页脚本、图片、字体、搜索索引和虚拟列表等后续建议，必须另有同条件证据才计作完成。

## 新增后台能力后的当前基线

以下是 2026-09-11 09:40 UTC 对当前生产 `.output` 的独立采样，用于后续变化时复核；**没有后台优化前对照组，不用于声称优化收益**。上文公开文章列表字段投影的配对证据仍单独成立。

工具为 `src/frontend/web-blog/tests/e2e/performance-admin.spec.ts`，通过既有 browser runner 创建隔离 PostgreSQL、媒体目录、账号、API 和生产前端。保留工厂原有 106 篇文章，新增一篇草稿后共 107 篇；管理列表实际显示每页 20 条。长文为 35,719 字符、81,991 UTF-8 字节，含 80 个正文二级标题，预览完整渲染，未删除内容或缩减分页规模。

运行条件：Windows x64、Node 24.16.0、Chromium 153.0.8010.12、Intel Core i5-14600KF（20 逻辑处理器），1440×1000 视口。每种页面先预热 1 次，再连续测量 3 次；同一浏览器上下文保留 HTTP 缓存，未清理操作系统或数据库缓存，无网络/CPU 节流及路由拦截。其他宿主工作负载未隔离，三次样本不构成性能阈值或生产 SLA。

客户端就绪由页面内 rAF 探针记录：工作台须出现真实 11 个草稿/待办数字和维护结果；列表须有实际 20 行；长文须有可编辑的完整 textarea 和正文内 80 个预览标题。资源快照再等待两个 rAF 回调后读取。该自定义就绪标记不是 FCP/LCP；也不要求所有后台预取达到 network idle。

三次中各页脚本的 Resource Timing `transferSize` 都为 0，表示此次读取来自已预热缓存；表中的编码/解码大小仍是这些资源的体积，**不能将缓存命中解释为首访不需要脚本**。API 每页均观察到 5 项资源，响应体编码/解码大小相同；对应 `transferSize` 为 4,837、7,670、86,193 字节。浏览器资源计数加文档请求分别为 194、182、181，其中各有一次无请求体的认证刷新 POST；这些计数包含缓存读取，不等于实际网络往返次数。导航阶段请求体合计为 0，初始建样本的 POST 不计入页面导航测量。报告不保存密码、令牌或原始请求正文。

长文输入使用真实可信的 `beforeinput/input` 事件，到后续第二个 rAF 回调的耗时为 **30.8、29.1、30.6 ms，中位数 30.6 ms**。它包含响应式更新与渲染调度，不是 INP、服务器保存时间，也不保证第二次绘制已经完成。每次在测量结束后以原生撤销还原完整正文；仅清理该隔离账号/文章的恢复副本，使下一次从相同已保存状态开始。默认自动保存功能未关闭，最终读取服务器确认正文仍完整且未被样本输入覆盖。
