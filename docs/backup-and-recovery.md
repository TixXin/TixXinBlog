# 备份与恢复

本项目提供内容迁入和完整恢复两种流程。当前开发库、管理员密码和现有文件不会在演练中被覆盖。

## 内容包：用于迁入新草稿

在 `/admin/maintenance` 下载 UTF-8 JSON 内容包，可选择是否包含受管图片。内容包包含当前文章、闪念、评论、目录及站点资料；不包含登录凭据、访客控制标识、修订历史和互动去重记录。

上传后先校验格式版本、大小、图片真实格式/摘要和引用，再展示明确预览。可选择跳过相同内容或创建新副本；文章与闪念始终迁入为新草稿。评论关系和审核状态保留，新副本重新累计阅读和点赞。目录遵循目标站点当前历史别名规则。正文链接保留原文，发布前需核对。

站点资料与评论审核设置默认不改动；勾选迁入设置后，预览显示将写入的公开资料，保存产生新的设置历史。执行绑定具体预览摘要，重新预览后旧确认失效。数据库变更统一提交，故障时回滚。票据重复执行返回既有结果，断线后可查询，不能凭响应丢失判断操作未执行。

单包最多 50MB、1000 篇文章、2000 条闪念、10000 条评论、300 个媒体；包含图片时总解码像素不超过 1 亿。更大的站点使用完整备份。预览有效期 15 分钟，完成或过期后清除临时包内容，保留票据摘要和结果。

## 完整备份：数据库与登记媒体

依赖 Node 24、固定版本 pnpm、Docker，以及运行中的 PostgreSQL 16 容器。本地容器默认 `tixxin-blog-postgres`，当前端口映射 15433。可通过 `BACKUP_POSTGRES_CONTAINER` 指定不同本机容器。

在仓库根目录执行：

```powershell
corepack pnpm --filter server-main run backup:full
```

默认在仓库 `.backups` 下创建全新目录。自定义目录必须不存在，建议传绝对路径：

```powershell
corepack pnpm --filter server-main run backup:full --output D:/PrivateBackups/tixxin-20260907
```

目录包含：

- `database.dump`：PostgreSQL custom 格式，包含所有 public 表、历史与认证记录。
- `media/`：所有登记的受管图片，包含回收状态的资源。
- `manifest.json`：格式版本、快照时间、表计数/内容摘要、数据库文件与媒体 SHA-256。

数据库导出使用同一 `pg_export_snapshot` 一致快照；快照固定后的新写入不会混入。媒体按快照中的登记清单复制和校验。文件缺失或摘要不符时不会生成完成清单。没有 `manifest.json` 的目录属于未完成备份。

备份中包含私人草稿及认证哈希，应存放在受控目录。源码、运行环境密钥、人工放入 `public` 的静态文件和外链图片不在数据备份范围，需要按各自来源保管。`.backups` 已从 Git 和 Docker 构建上下文排除。

## 校验与隔离恢复

仅恢复可信来源的备份；校验和用于检测完整性，不能证明来源。

```powershell
corepack pnpm --filter server-main run backup:verify --directory D:/PrivateBackups/tixxin-20260907
corepack pnpm --filter server-main run backup:restore --directory D:/PrivateBackups/tixxin-20260907
```

恢复命令使用本机已有的官方 `postgres:16-alpine` 或 `postgres:16` 镜像，新建专用数据卷和 `tixxin-restore-<UUID>` 容器。容器使用 `network=none`，不暴露网络端口。原数据库、原媒体目录和原容器保留。

恢复过程校验全部表行数与内容摘要，复制并校验媒体，再撤销恢复出来的访问/刷新授权，递增账号会话版本，并轮换内容上下文。密码哈希按备份原样恢复；原库密码不修改。旧页面即使重新登录也必须刷新读取恢复后的内容，不能继续提交旧数据上下文。

输出目录包含 `restore-report.json`、`connection.json` 和恢复后的 `media`。`connection.json` 含新隔离数据库的本地配置，仅适用于该隔离容器网络空间，不应发布。恢复命令不会自动修改应用环境。

## 切换与回退

正式切换应由操作者在核对恢复报告后执行：

1. 保留当前库的最新完整备份，停止所有原 API 实例，避免切换期间继续写入旧库。
2. 保留隔离恢复卷，通过受控容器网络连接需要使用它的 API；勿将数据库端口开放到公网。
3. 使用恢复目录中的连接资料配置 API，并将媒体目录指向恢复后的 `media`。使用与备份匹配的代码版本；升级代码时先回放新增迁移并检查 schema。
4. 启动服务并验证 `/ready`、公开文章/图片及管理登录。所有旧登录授权已撤销，管理页面需刷新。
5. 需要回退时停止 API，重新指向保留的原库与原媒体目录。不要直接删除原数据或覆盖备份目录。

完整恢复是备份时刻的数据状态；如果备份之后修改过密码，需要使用备份时的账号资料处理恢复目标。切换不在自动演练范围内。

## 可重复演练与诊断

```powershell
corepack pnpm --filter server-main run test:backup-restore
```

演练创建随机命名的隔离源库，验证并发新文章不进入既有快照、篡改文件被拒绝、全部表摘要及媒体一致。恢复容器和卷带任务标签，测试只清理自己创建且标签匹配的资源。报告留在 `.backups/verification-*/verification-report.json`。

后台运行诊断只向管理员展示数据库连通性、待应用迁移、schema 一致性、Node 版本和存储读写探测。媒体完整性核验单独读取登记资源，返回缺失/损坏的资源编号，不公开磁盘路径或连接凭据。

恢复后的媒体目录默认仅归创建用户访问；将其挂载到容器时，需让运行 API 的用户具有读取权限。可设置 `RESTORE_API_IMAGE` 运行当前后端镜像的隔离应用验证；验证会共享恢复容器的无外部网络空间，不发布端口。CI 同时检查数据库、媒体和旧授权拒绝。
