这个博客的第一个 commit 是 2024 年 3 月，当时只有一个 `app.vue` 和一篇用 Markdown 写的“你好世界”。两年半过去，它变成了一个 Nuxt 前端加 NestJS 后端的 monorepo，有后台、图库、留言板和三套主题。中间换过一次数据层，重写过一次主题系统，踩的坑足够写一篇长文。趁着九月不忙，把整个过程捋一遍，重点放在那些文档里没写、要自己撞一次才知道的地方。

先说一下现在的技术栈，方便后面对照：Nuxt 4、Vue 3.5、TypeScript，后端是 NestJS 加 MikroORM 加 PostgreSQL，包管理用 pnpm workspace，部署在一台自己的 Linux 小服务器上。

## 第一阶段：纯静态，Markdown 文件就是数据库

最早的版本没有后端。文章是仓库里的 `.md` 文件，用 Nuxt Content 读取，`nuxt generate` 生成静态页面扔到服务器上。这个方案对于“只想写文章”的人是最省心的，我用了大概半年。

离开它的原因是评论。静态站要评论就得接第三方服务，我试过两个，一个要加载 300 多 KB 的脚本，另一个把访客的邮箱发到了国外的服务器。我想要一个自己管数据的评论区，这就必须有后端了。

如果你现在要开始一个博客，而且不打算做评论、留言这类需要写入的功能，我仍然推荐静态方案。后端带来的运维成本比想象中高。

## 第二阶段：加后端，把前后端拆开

选 NestJS 是因为它和 Nuxt 的心智模型接近，都是约定大于配置，而且 TypeScript 原生。ORM 一开始用的是 Prisma，后来换成了 MikroORM，原因后面说。

目录结构定成这样：

```bash
src/
  frontend/web-blog/    # Nuxt 应用
  backend/server-main/  # NestJS 应用
pnpm-workspace.yaml
package.json            # 根目录只放 workspace 脚本
```

前后端各自独立运行，开发时前端走 Nuxt 的 devServer 代理把 `/api` 转到后端的 3001 端口，生产环境由 Nginx 做同样的事。这一步最大的坑是 SSR 时的请求路径。浏览器里 `$fetch('/api/posts')` 会走代理，但服务端渲染时这个请求发生在 Node 进程里，没有代理，相对路径会直接失败。解决办法是在 `nuxt.config.ts` 里给 Nitro 配 `routeRules` 的 `proxy`，让服务端请求也能找到后端：

```ts
export default defineNuxtConfig({
  nitro: {
    routeRules: {
      '/api/**': { proxy: `${process.env.API_ORIGIN ?? 'http://127.0.0.1:3001'}/**` },
    },
  },
})
```

另一个相关的坑是访客 IP。SSR 时后端看到的请求来自 Nuxt 进程，不是访客，限流和访问统计全都记在了 127.0.0.1 上。我在 Nuxt 的服务端请求里把原始的 `x-forwarded-for` 透传给后端，后端再信任这个头，才把访客身份接上。

## 第三阶段：数据层的两次返工

Prisma 换 MikroORM 发生在 2025 年初。直接原因是迁移文件。Prisma 的迁移是 SQL 文件，改一次字段生成一份，半年下来积累了四十多份，而且有几次自动生成的 SQL 会先删列再加列，线上数据差点丢。MikroORM 的迁移是 TypeScript，可以手写 `up` 和 `down`，还能在迁移里跑数据搬运逻辑。换过去之后我给每个迁移都补了 `down`，回滚终于可用了。

第二次返工是内容包。我想要一个“把整站内容导出成一个文件、换台服务器导入就能恢复”的功能。第一版导出的是数据库表的直接映射，结果后来每改一次表结构，旧的导出文件就不能导入了。第二版加了版本号，导入时按版本做转换，现在导出 v11，能接受 v1 到 v10 的旧包。这个版本号机制是我在整个项目里最庆幸做了的决定之一，它让我敢放心改表结构。

> 教训：任何会持久化到用户手里的数据格式，第一天就要带版本号。

## 第四阶段：主题系统和后台

三套主题不是一开始就有的。第一套主题写死在组件里，第二套是复制了一份整个 `components` 目录再改，改到第三套的时候我终于受不了了。现在的方案是 Nuxt Layers：每套主题是一个独立的 layer，只覆盖布局和少量组件，业务逻辑和数据获取在主应用里，主题之间共用。切换主题只是改一个环境变量，重新构建。

```ts
// themes/nexus/nuxt.config.ts
export default defineNuxtConfig({
  extends: ['../../app'],
  components: [{ path: './app/components', prefix: '' }],
})
```

这里有一个和 Nuxt 4 相关的坑：4 把默认源目录从根目录移到了 `app/`，layer 的路径也要跟着改，升级那天我花了两个小时才搞清楚为什么主题的组件全部找不到。

主题之间还有一个“主题契约”的约定：每套主题必须提供同样一组布局和插槽名，主应用只认契约不认实现。这样加第四套主题时不需要改任何业务代码，只要把契约里的东西实现一遍。契约我写在了一个 TypeScript 接口里，主题的入口文件用 `satisfies` 对一下，少实现一个插槽编译就过不去。

后台放在同一个 Nuxt 应用的 `/admin` 路由下，用路由中间件判断登录状态，没登录就重定向。本来考虑过单独做一个后台应用，但对单博主来说多维护一个应用不值得。登录用的是 JWT 放在 HttpOnly Cookie 里，刷新令牌单独一个 Cookie，这套做法后端写了一天，前端只加了一个中间件。

## 性能和部署

上线后遇到的第一个性能问题是 SSR 的重复请求。首页要拉文章列表、侧栏要拉最近评论、页脚要拉站点统计，每个页面刷新都是三个后端请求。后来加了 60 秒的服务端页面缓存，按路径和 Cookie 分键，写请求之后清空。缓存命中时首页的服务端响应从 120 毫秒降到 8 毫秒，后端的查询量少了九成。

部署用 GitHub Actions 推到服务器，Nginx 反代，前后端各一个 systemd 服务。这部分我之前写过一篇专门的文章，这里不展开。有一个和 Nuxt 相关的细节值得提：`.output` 目录是自包含的，不需要在服务器上装依赖，但 `NUXT_PUBLIC_` 开头的环境变量在构建时就固定了，运行时改不了，所以站点 URL 这类配置得在构建阶段给。

## 如果重来一次

- 会从第一天就用 monorepo，前后端分仓的那三个月，类型同步全靠复制粘贴。
- 会直接用 MikroORM，少走 Prisma 迁移的弯路。
- 会更早做内容包的版本号，而不是等到第一次导入失败。
- 不会再复制一整套组件去做主题，Layers 从一开始就是正确答案。
- 会更早把性能数据记下来，前半年的优化没有留下任何数字，现在说不清哪些改动有效。

两年半下来，这个项目最大的价值不是博客本身，而是它成了我试新东西的地方。Nuxt 4 的 alpha、Vue 3.5 的新响应式、MikroORM 的新版本，都是先在这里跑一遍再敢用到工作里。它不需要完美，只需要一直在。
