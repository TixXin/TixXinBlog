这个博客从去年底开始重写，技术选型的时候我在样式方案上纠结了差不多两周。公司项目这两年基本都在用 Tailwind，我自己也写得很顺手，按理说没什么好犹豫的。但博客这个项目有几个和公司项目完全不一样的地方，想清楚之后我选了 SCSS。半年用下来，我觉得这个决定是对的，这篇写写为什么。

先声明，这不是一篇“Tailwind 不好”的文章。我在公司项目里还在天天用它，而且用得很开心。这篇只是说，在博客这个特定场景下，我为什么觉得 SCSS 更合适。

## 博客和业务项目的不同

公司项目的典型特征是：人多，页面多，迭代快，设计稿来自统一的设计系统。Tailwind 在这种场景下的优势很明显，所有人写出来的样式长得一样，不用起名字，不用担心样式冲突，复制一段 HTML 到另一个页面效果完全一致。

博客的特征正好相反：一个人写，页面不多，但每个页面都想做得有点个性。而且博客有一个业务项目很少有的需求：**多主题**。我想让读者在三套视觉风格之间切换，不只是深色浅色，而是排版、配色、间距节奏都不一样的三套皮。

这个需求在 Tailwind 里当然也能做，但做法会很别扭。Tailwind 的工具类是把样式决定写在 HTML 里，而多主题的本质是同一份 HTML 对应不同的样式决定。要么用 CSS 变量加大量的 `bg-[var(--surface)]` 这类任意值写法，要么给每个主题写一套 `theme-a:bg-white theme-b:bg-stone-100` 的变体，前者等于绕过了 Tailwind，后者的 class 列表会长到没法读。

## SCSS 在这件事上的做法

用 SCSS 的话，这个问题就是它的主场。我现在的结构大概是这样：

```text
app/assets/styles/
  _tokens.scss        # 设计变量，输出成 CSS 自定义属性
  _mixins.scss        # 断点、文字截断这类工具
  themes/
    _nexus.scss       # 主题一
    _paper.scss       # 主题二
    _terminal.scss    # 主题三
  main.scss
```

每个主题文件只做一件事：给 `:root[data-theme='xxx']` 赋一组 CSS 变量。组件里只引用变量，不关心当前是哪个主题：

```scss
// themes/_paper.scss
:root[data-theme='paper'] {
  --color-surface: #f7f3ec;
  --color-text: #2b2520;
  --color-accent: #b5542d;
  --font-body: 'Noto Serif SC', serif;
  --radius-card: 2px;
  --space-section: 4.5rem;
}
```

```scss
// components/post/PostCard.vue 里的样式
@use '~/assets/styles/mixins' as m;

.post-card {
  background: var(--color-surface);
  border-radius: var(--radius-card);
  padding: var(--space-card);

  &__title {
    font-family: var(--font-heading);
    @include m.line-clamp(2);
  }

  @include m.below('md') {
    padding: calc(var(--space-card) * 0.75);
  }
}
```

切主题就是改 `data-theme` 属性，组件代码一行不动。这是我选 SCSS 最核心的原因：**样式决定留在样式文件里，HTML 只描述结构**。对于一个要维护三套皮的项目来说，这种分离不是洁癖，是刚需。

有一个细节值得补充。三套主题不只是颜色不同，排版节奏也不一样：paper 主题用衬线字体、更大的行高和更窄的正文宽度，terminal 主题用等宽字体、几乎没有圆角、间距紧凑。这些差异全部通过变量表达，`--font-body`、`--radius-card`、`--space-section` 这几个变量在每个主题文件里的值不同，组件完全不感知。我试过把其中一套主题用 Tailwind 的变体重写了一个页面，光是一个卡片组件的 class 就超过了四十个，看了一眼就放弃了。

## 几个具体的体验差异

用了半年，有几点感受比较具体。

**改设计的时候。**博客的设计是我自己一边写一边调的，经常是看着页面觉得这里间距不对，改一下。SCSS 的工作流是打开那个组件的样式块，改一个值，整站生效。Tailwind 的工作流是找到所有用了 `gap-6` 的地方，判断哪些该改哪些不该改。前者在“一个人反复调”的场景下明显更顺。

**读代码的时候。**我写博客的频率不固定，有时候一个月不碰，回来再看代码。SCSS 的 `.post-card__title` 一眼知道是什么；Tailwind 的一长串 class 需要在脑子里重新渲染一遍。不是说 Tailwind 的不可读，而是对一个经常离开再回来的人来说，有名字的东西更容易捡起来。

**构建产物。**这一点 Tailwind 反而更有优势。它的 JIT 模式只生成用到的类，产物很小。SCSS 这边我得自己注意不要写重复的样式。目前博客全部样式压缩后 38KB，三套主题在内，我觉得可以接受，但如果换成 Tailwind 大概能再小一些。

**动态样式。**博客有些地方需要根据数据决定样式，比如标签的颜色、阅读进度条的宽度。这类东西在哪边都是用内联 style 或 CSS 变量解决，差别不大。

## Tailwind 真正好的地方

公平起见，说说我在公司项目里离不开 Tailwind 的几个原因。

一是**约束**。它的间距刻度、色阶、字号都是预设好的，新人写出来的页面不会出现 13px 和 15px 混用的情况。SCSS 这边我得靠自律，`_tokens.scss` 里定了刻度，但没人拦着你写 `padding: 13px`。

二是**协作成本**。十个人的项目，用 Tailwind 几乎不会有样式冲突，也不用讨论命名规范。我们之前用 BEM 的时候，光是 `__` 和 `--` 该怎么用就争过好几轮。

三是**快**。做原型、做内部工具、做一个明天就要上的活动页，Tailwind 的速度没有对手。写 HTML 的时候顺手就把样式带上了，不用在两个文件之间跳。

所以我的结论是，这不是一个“哪个更好”的问题，而是“项目的瓶颈在哪”的问题。公司项目的瓶颈是协作和一致性，Tailwind 直接解决；博客的瓶颈是多主题和一个人长期维护的可读性，SCSS 更顺手。

## 如果你也在选

给几条我自己的判断标准，供参考：

- 需要多套视觉主题而不只是深浅色切换，倾向 SCSS 或原生 CSS 加变量。
- 团队三人以上且没有专职设计系统维护者，倾向 Tailwind。
- 页面数量多但每页都差不多，倾向 Tailwind；页面不多但每页都想不一样，倾向 SCSS。
- 自己一个人长期维护、会反复离开再回来，倾向有命名的方案。

还有一个折中选项我没采用但觉得值得一提：用 Tailwind 的 `@apply` 把常用组合封装成有名字的类。这样既能享受它的刻度约束，又能有可读的命名。我没用是因为它等于用 Tailwind 的语法写 SCSS，两边的好处都只拿到一半。

半年下来，博客的三套主题跑得很稳，新增第四套的话我估计一个下午就能搞定，因为只需要再写一个变量文件。这种“加一套皮只改一个文件”的感觉，是我当初选 SCSS 时想要的，现在也确实拿到了。
