博客的文章卡片组件我改过至少五次。它出现在首页的双栏列表里、侧栏的“相关文章”里、搜索结果的单栏里，还有后台的管理表格里。同一个组件，四种宽度，以前只能靠媒体查询硬猜：视口大于 1024 时侧栏大概是 280 像素宽，那就在 1024 这个断点把侧栏里的卡片改成竖排。可是一旦侧栏宽度调整，或者卡片被放进一个新地方，断点就全错了。

Container Queries 解决的就是这件事。它让组件根据自己所在容器的尺寸调整样式，而不是根据视口。这个特性在 2023 年初就被所有主流浏览器支持了，到今天已经不需要考虑兼容问题，但我发现身边用它的人还是不多。这篇把我在博客里用它的几个场景写出来。

## 基本用法：两行声明

容器查询分两步。先在父元素上声明它是一个容器，再在子元素的样式里写 `@container` 规则。

```css
.card-list {
  container-type: inline-size;
  container-name: card-list;
}

.card {
  display: grid;
  grid-template-columns: 120px 1fr;
  gap: 16px;
}

@container card-list (width < 360px) {
  .card {
    grid-template-columns: 1fr;
  }
  .card__cover {
    aspect-ratio: 16 / 9;
  }
}
```

`container-type: inline-size` 表示只按行内方向（通常是宽度）建立查询容器。几乎所有场景用这个就够了，`size` 要同时约束高度，会让容器的高度不再由内容撑开，一般不要用。`container-name` 可以省略，省略时 `@container` 会往上找最近的容器，但我习惯都写上，组件嵌套多了之后能避免查到错误的祖先。

上面那段写完，卡片在首页的双栏里是横排，被放进 280 像素的侧栏时自动变成竖排，搜索页的单栏是横排，后台表格里的 200 像素单元格又变成竖排。四个地方，一份样式，没有任何一处需要知道视口多宽。

## 和媒体查询的分工

容器查询不是要取代媒体查询。我现在的分工是：页面级布局用媒体查询，组件级样式用容器查询。

页面级布局指的是“侧栏什么时候折到下面”“导航什么时候变成汉堡菜单”这种和整个页面结构相关的决定，它们天然和视口有关。组件级指的是“这个卡片是横排还是竖排”“这个表格是否隐藏次要列”，它们只和组件被放在多大的地方有关。

有一个判断标准很好用：如果一个组件可能出现在两个以上宽度不同的位置，它的样式就应该用容器查询。只出现在一个固定位置的，用什么都行。

另一个需要注意的点是性能。容器查询在布局阶段多了一轮计算，理论上比媒体查询贵。我用 Chrome 的性能面板测过文章列表页，一百张卡片的情况下，布局时间从 2.1 毫秒涨到 2.4 毫秒，可以忽略。但如果容器嵌套很深、每一层都是容器，开销会累积，所以只在真正需要查询的层级声明 `container-type`，不要图方便给每个 div 都加上。

## 容器查询单位

和 `vw`、`vh` 对应，容器查询有 `cqw`、`cqh`、`cqi`、`cqb` 这几个单位，分别是容器宽度、高度、行内尺寸、块尺寸的百分之一。我用得最多的是 `cqi`，拿来做随容器缩放的字号。

```css
.card__title {
  font-size: clamp(14px, 4cqi, 20px);
  line-height: 1.4;
}
```

这行的意思是标题字号跟着容器宽度走，容器 400 像素时是 16 像素，但最小 14、最大 20。以前要做这种效果得用 JS 监听尺寸再算字号，现在一行 CSS，而且没有闪烁。在侧栏里标题自动小一号，在首页大一号，不用写任何断点。

要注意 `cqi` 必须在一个查询容器的后代里才有意义，如果祖先里没有声明 `container-type`，它会退化成按视口计算，效果就和 `vi` 一样了。这个退化是无声的，排查起来比较烦，我吃过一次亏，就是把卡片单独拿出来写 demo 时忘了包容器。

## 样式查询：根据自定义属性切换

容器查询还有另一半，样式查询，语法是 `@container style(--foo: bar)`。它查的不是尺寸而是容器上某个自定义属性的值。博客的三套主题切换就用到了它。

每套主题在根元素上设一个 `--card-style`，值是 `plain`、`outlined` 或 `elevated`，卡片组件内部按这个值改自己的边框和阴影：

```css
.card {
  border-radius: var(--radius-md);
}

@container style(--card-style: outlined) {
  .card {
    border: 1px solid var(--line);
  }
}

@container style(--card-style: elevated) {
  .card {
    box-shadow:
      0 1px 2px rgb(0 0 0 / 0.06),
      0 8px 24px rgb(0 0 0 / 0.08);
  }
}
```

以前这种事要么靠主题 class 层层嵌套选择器，要么每套主题复制一份卡片样式。样式查询让组件自己决定“在这种主题下我长什么样”，主题只负责声明属性。目前只支持查询自定义属性，不支持查 `color` 这类普通属性，不过自定义属性对主题切换已经够用了。样式查询的浏览器支持比尺寸查询晚，今年之前 Firefox 一直没跟上，现在已经全线支持，可以放心用。

## 在 Vue 组件里的组织方式

容器查询让“组件自带响应式”成为可能，所以我把容器的声明也放进了组件内部。卡片组件的根元素外面包一层 `.card-shell`，由它来声明 `container-type`，卡片本身的所有查询都基于这个壳。这样无论卡片被放到哪里，它都带着自己的容器，父级不需要知道任何事。代价是多一层 DOM，对一个列表组件来说可以接受。如果列表本身已经是一个容器，壳就可以省掉，用 props 控制要不要渲染它。

## 几个踩过的坑

- 容器查询的容器本身不能用自己的查询。`.card-list` 声明了容器，`@container` 里就不能改 `.card-list` 自己的样式，只能改它的后代。想改自己，要在更外层再包一个容器。
- `container-type: inline-size` 会给元素建立新的包含块和尺寸隔离，`position: absolute` 的子元素定位基准会变，`width: auto` 的表格可能被撑坏。遇到奇怪的布局问题先看是不是刚加了容器声明。
- 浮动和 `display: contents` 的元素不能当容器。
- 在 Vue 的单文件组件里用 `scoped` 样式写 `@container`，容器名要在同一个组件里声明，跨组件的容器名因为 `scoped` 的属性选择器会匹配不上，要么用全局样式，要么在父组件里用 `:deep`。

把卡片组件重写完之后我数了一下，样式文件从 212 行减到 140 行，删掉的大部分是针对各个位置的媒体查询覆盖。更重要的是，上周把卡片放进一个新的“专栏精选”区块时，我一行样式都没改，它自己就排对了。响应式设计的核心问题从来不是“屏幕多宽”，而是“这个东西被放在多大的地方”，容器查询终于让 CSS 能够回答后面这个问题。
