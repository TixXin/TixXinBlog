去年底把博客的反向代理从 Nginx 换到了 Caddy，顺手打开了 HTTP/3。当时只是因为 Caddy 默认就开，没想太多。春节期间回老家，老家的宽带不太稳，我用手机热点刷自己博客的时候明显感觉比以前顺，回来一查 DevTools，Protocol 那列全是 `h3`。这让我有了兴趣去认真搞清楚 HTTP/3 和它底下的 QUIC 到底做了什么，以及对我这种小站到底有没有实际意义。

这篇是我的学习笔记加上一些实测数据，面向和我一样“听说过但没细看”的开发者。

## TCP 的队头阻塞到底卡在哪

先说 HTTP/2 解决了什么、没解决什么。HTTP/1.1 一个连接同时只能处理一个请求，浏览器靠开六个连接并行。HTTP/2 在一个 TCP 连接里做了多路复用，几十个请求的帧交错着发，连接数降下来了，头部也压缩了。

但它底下还是 TCP。TCP 的承诺是“字节流按序、可靠到达”，这意味着只要中间有一个包丢了，后面所有已经到达的包都得在内核缓冲区里等那个丢的包重传回来，哪怕后面的包属于另一个完全无关的请求。HTTP/2 把所有请求塞进一条流，反而把这个问题放大了：丢一个包，整页所有资源一起停。这就是传输层的队头阻塞。

在有线网络里丢包率很低，这不是大问题。在手机、地铁、老家那种信号飘忽的网络里，1% 到 3% 的丢包很常见，HTTP/2 的表现有时候还不如开六个连接的 HTTP/1.1。

## QUIC 换掉了地基

QUIC 的思路是不改 TCP，而是在 UDP 上面重新实现一套可靠传输，把“流”这个概念从 HTTP 层下沉到传输层。每个流独立做可靠性保证，流 A 丢了包只阻塞流 A，流 B 的数据照常往上交付。HTTP/3 本质上就是 HTTP/2 的语义搬到 QUIC 上，帧格式和头部压缩（从 HPACK 换成了 QPACK）做了相应调整。

除了解决队头阻塞，QUIC 还做了几件以前在 TCP 上做不到或者做得很别扭的事：

- **握手合并。** TLS 1.3 直接内建在 QUIC 里，连接建立和加密协商在同一个往返里完成，首次连接 1-RTT，重连可以 0-RTT。TCP 加 TLS 1.3 最少要 2-RTT。
- **连接迁移。** QUIC 连接用一个 Connection ID 标识，不绑定四元组。手机从 Wi-Fi 切到 5G，IP 变了，连接不断。TCP 换 IP 就得重连。
- **拥塞控制在用户态。** 不用等操作系统内核升级，服务端软件自己就能换算法，Caddy 用的 `quic-go` 默认是 Cubic，也可以切 BBR。
- **全程加密。** 连包头的大部分字段都加密了，中间设备看不到也改不了，副作用是运营商的一些“优化”没法做，有时候反而是好事。

## 实际能快多少

理论说完，看数据。我用博客的文章页来测，页面总共请求 23 个资源，传输 410KB。工具是 Chrome 的 DevTools 和 `curl --http3`，网络环境分三种：公司办公室的有线、家里的 Wi-Fi、老家用手机热点。每种环境各刷 20 次取中位数，对比的是 Caddy 开 h3 和强制 h2 两种配置下的 DOMContentLoaded：

| 环境         | 丢包率（估） | HTTP/2 | HTTP/3 | 提升 |
| ------------ | ------------ | ------ | ------ | ---- |
| 办公室有线   | 接近 0       | 312ms  | 298ms  | 4%   |
| 家里 Wi-Fi   | 约 0.5%      | 468ms  | 401ms  | 14%  |
| 老家手机热点 | 约 2%        | 1340ms | 890ms  | 34%  |

有线环境几乎没差别，省的那十几毫秒基本是握手少了一个往返。网络越差差距越大，热点环境下三分之一的提升是肉眼可感的。这个结论和我听到的说法一致：HTTP/3 的价值主要在弱网，不在机房。

另一个有意思的观察是重连。我把 Caddy 重启一次再刷页面，HTTP/3 用 0-RTT 把首字节时间压到了 60ms 左右，HTTP/2 需要重新走 TCP 握手加 TLS，大概 180ms。对经常切后台再回来的移动端用户，这个差别会反复出现。

## 服务端怎么开

Caddy 是最省事的，v2 默认开启 HTTP/3，只要你的服务器放行 UDP 443，`Caddyfile` 不用加任何东西。我的配置就是普通的反代：

```text
blog.example.test {
  encode zstd gzip
  reverse_proxy localhost:3000
}
```

防火墙那一步最容易漏。我一开始 `ufw` 只开了 `443/tcp`，Caddy 日志里也不报错，浏览器就是用 h2。加了 `443/udp` 之后才切过去。可以用 curl 验证：

```bash
curl -sI --http3 https://blog.example.test | head -1
# HTTP/3 200
```

需要 curl 8.x 并且编译时带了 QUIC 支持，macOS 用 Homebrew 装的 `curl` 默认就有。

Nginx 从 1.25 开始内建 QUIC 模块，配置是在 `listen` 上加 `quic` 并发送 `Alt-Svc` 头告诉浏览器可以升级：

```nginx
server {
    listen 443 ssl;
    listen 443 quic reuseport;
    http2 on;
    add_header Alt-Svc 'h3=":443"; ma=86400';
    ssl_protocols TLSv1.3;
}
```

浏览器第一次访问还是走 HTTP/2，看到 `Alt-Svc` 之后下次才尝试 HTTP/3，所以第一次刷看到 h2 不要慌。

如果你在用 CDN，情况更简单，主流厂商的控制台里都有一个开关，打开之后边缘节点到用户这段就是 HTTP/3，源站到 CDN 之间仍然可以是 HTTP/1.1。对大多数用户来说，决定体验的恰恰是最后那一跳。

## Node.js 这边的情况

Node 自己呢？目前（25.x 之前）核心模块还没有稳定可用的 HTTP/3 服务端实现。2021 年曾经有一个实验性的 QUIC 模块合进去又被移除了，后来基于 ngtcp2 的实现一直在推进，但还没到能在生产用的程度。所以现实的做法就是我现在这样：Node 应用继续用 HTTP/1.1 或 HTTP/2 跑在内网，前面放 Caddy 或者 Nginx 做 HTTP/3 终结。对应用代码来说完全透明，连 `req.httpVersion` 都还是 `1.1`。

客户端方面 `fetch` 也不会主动走 HTTP/3，Node 的 `undici` 目前只支持 HTTP/1.1 和部分 HTTP/2。如果你的 Node 服务需要以 HTTP/3 客户端的身份去调别人的接口，暂时只能借助 curl 或者其他语言的库。

另外要小心 0-RTT 的重放风险。0-RTT 数据在服务端收到之前可能被中间人复制重发，所以这部分请求必须是幂等的。浏览器只会把 GET 这类安全方法放进 0-RTT，但如果你的 GET 接口有副作用（比如“访问一次就计数一次”），就得自己加防护。我博客的阅读计数接口就是因为这个从 GET 改成了 POST。

## 要不要开

对小站来说这是一个没什么成本的开关：Caddy 默认就开，Nginx 加两行，CDN 厂商基本都支持。收益在弱网和移动端，桌面有线环境几乎无感。我的博客流量里手机占六成，所以开了之后整体的 75 分位加载时间降了大约 15%，算是意外之喜。

需要注意的只有两件事：UDP 443 要放行；有些企业网络和公共 Wi-Fi 会屏蔽 UDP，这时浏览器会自动回落到 HTTP/2，不需要你做什么，但排查“为什么这个用户看到的是 h2”的时候要想到这一层。

搞明白这些之后再回头看老家那次“感觉更顺了”的体验，终于知道是怎么回事。不是错觉，是丢掉的那几个包不再拖着整页一起等了。
