上个月给团队新人做分享，讲到“为什么这个列表滚动起来会掉帧”，我画了一张从 HTML 到像素的流程图，讲完发现自己有几个环节其实也只是“大概知道”。回头把 Chromium 的 RenderingNG 文档和几篇源码解读翻了一遍，顺便用 DevTools 的 Performance 面板对着自己博客的页面逐帧看，终于把这条管线在脑子里串顺了。这篇文章是那次梳理的整理版，重点放在每个阶段对性能的影响，以及写 CSS 和 JS 的时候该怎么避开那些昂贵的操作。

## 管线的大致样子

浏览器拿到一个页面，到把它画在屏幕上，主线程上大致要经过这些阶段：

1. **解析**：HTML 变成 DOM 树，CSS 变成 CSSOM。
2. **样式计算（Style）**：为每个 DOM 节点算出最终生效的样式值。
3. **布局（Layout）**：根据样式算出每个盒子的几何信息——位置和大小。
4. **分层（Layer）**：决定哪些内容需要单独的合成层。
5. **绘制（Paint）**：生成绘制指令列表，告诉光栅化器“在这里画一个圆角矩形，填这个颜色”。
6. **合成（Composite）**：把各层光栅化后的位图按顺序叠起来，交给 GPU 显示。

前五个阶段在渲染主线程上跑，最后一个合成阶段在单独的合成线程上，这是理解“为什么有的动画不卡”的关键。

如果你在 Performance 面板里录一段，会看到紫色的 Recalculate Style 和 Layout、绿色的 Paint 和 Composite Layers，它们加起来就是一帧要花的时间。60Hz 的屏幕一帧的预算是 16.7ms，这里面还要扣掉 JS 执行的时间，所以留给渲染的往往只有几毫秒。

## 解析阶段：为什么 CSS 会阻塞渲染

HTML 解析是流式的，边下载边建 DOM。但遇到 `<link rel="stylesheet">` 时，虽然 DOM 可以继续建，渲染树的构建必须等 CSSOM 完成——浏览器不能在不知道样式的情况下画东西，否则会先画出一个无样式页面再闪一下。这就是 CSS 被称为“渲染阻塞资源”的原因。

而 `<script>` 更凶一点：默认情况下遇到同步脚本，HTML 解析直接暂停，因为脚本可能 `document.write`。如果脚本前面还有没加载完的 CSS，脚本还得等 CSS（因为脚本可能读样式）。所以“CSS 阻塞脚本，脚本阻塞解析”这条链是首屏慢的常见原因。

我博客的做法是：关键 CSS 内联在 `<head>` 里，其他样式用 `media="print"` 加 `onload` 切回的技巧延后加载，脚本一律 `type="module"`（默认 defer）。这几个改动让首屏的 FCP 从 1.4s 降到了 0.9s（本地 4G 模拟，Nuxt 生成的静态页）。

## 样式计算与选择器匹配

样式计算要做两件事：为每个元素找出所有匹配的规则，再按层叠规则算出最终值。选择器匹配是从右向左的，`.list .item span` 会先找出页面上所有 `span`，再逐个往上找祖先是否有 `.item` 和 `.list`。

这意味着两点：

- 选择器最右边那个“键选择器”越具体越好。`.card-title` 比 `.card h3` 快，因为后者会先匹配所有 `h3`。
- 后代选择器嵌套太深会让每个候选元素都向上遍历很多层。

不过我得说句实话：对于几千个节点的普通页面，选择器性能的差别基本测不出来。真正会让 Recalculate Style 变贵的是**改了一个影响面很大的样式**——比如在 `body` 上切换一个 class，那所有后代都要重新算一遍。我在博客切换主题时就遇到过这个问题，一次切换要 40ms 的样式重算，后来把主题变量限定在 `:root` 的 CSS 自定义属性上，切换时只有引用了这些变量的属性需要重算，降到了 8ms。

## 布局：回流是怎么发生的

布局阶段算几何信息。只要有任何会影响位置和尺寸的东西变了——宽高、边距、字体大小、`display`、甚至窗口尺寸——受影响的子树就要重新布局，这就是回流（reflow）。

回流本身不可怕，可怕的是**强制同步布局**。浏览器正常情况下会把一帧里所有样式修改攒起来，到帧末统一布局一次。但如果你在修改样式之后马上读取一个依赖布局的属性（`offsetHeight`、`getBoundingClientRect()`、`scrollTop` 等），浏览器为了给你一个正确的值，必须立刻执行一次布局。在循环里这么干，就是所谓的布局抖动（layout thrashing）：

```js
// 坏：每次循环都触发一次同步布局
for (const item of items) {
  const width = container.offsetWidth // 读
  item.style.width = `${width / 2}px` // 写，让布局失效
}

// 好：先集中读，再集中写
const width = container.offsetWidth
for (const item of items) {
  item.style.width = `${width / 2}px`
}
```

我用这个思路改过一个瀑布流组件，原来每插入一张图就读一次列高，300 张图初始化要 600ms 左右，改成批量读写之后只要 70ms。Performance 面板里能很直观地看到：改之前是几百个紫色小块排成一排，每个前面都有个红色三角警告“Forced reflow”；改之后只剩一个。

另外，`contain` 属性在布局阶段非常有用。给一个独立的卡片加上 `contain: layout`，告诉浏览器“这个盒子内部的变化不会影响外面”，回流的范围就被限制在卡片里了。长列表的每一项上加 `content-visibility: auto`，屏幕外的项直接跳过布局和绘制，首屏布局时间可以降一个数量级。

## 绘制与合成：动画为什么要用 transform

绘制阶段生成的是绘制指令，真正的光栅化（把指令变成位图）在光栅线程上做。合成阶段把多个层的位图叠起来，这一步在合成线程上，跟主线程无关。

这就是为什么 `transform` 和 `opacity` 的动画几乎不掉帧：它们只改变层的变换矩阵和透明度，不需要重新布局，也不需要重新绘制，合成线程自己就能完成。而动画 `left`、`width` 或者 `box-shadow`，每一帧都要重走布局或绘制，主线程一旦忙起来（比如在跑 JS），动画就卡住了。

```css
/* 每帧都要重新布局 */
.slide-in {
  transition: left 300ms ease-out;
}

/* 只在合成线程上做 */
.slide-in {
  transition: transform 300ms ease-out;
  will-change: transform;
}
```

`will-change` 的作用是提前把元素提升到单独的合成层，避免动画开始那一瞬间的层创建开销。但它不能滥用——每个合成层都要占显存，我曾经在一个页面上给几十个卡片都加了 `will-change: transform`，Layers 面板里显示显存占用超过 200MB，低端安卓机直接黑屏。现在的原则是：只给真正在动的元素加，动画结束后移除。

还有一个经常被忽略的开销是**绘制区域**。DevTools 的 Rendering 面板里开启“Paint flashing”，页面上每次重绘的区域会闪绿色。如果你滚动一下列表发现整个页面都在闪，说明有个什么东西（通常是固定定位的头部或者一个巨大的阴影）让整页都被标记为脏区域了。把那个元素单独提升为一层，通常就能解决。

## 把这些串起来看一次实际案例

拿我博客的文章列表页说。最初版本滚动时帧率在 40 左右，录了一段 Performance 之后发现三个问题：

- 顶部导航用 `backdrop-filter: blur()` 做了毛玻璃，这个效果每帧都要重新光栅化它背后的内容；
- 每张卡片的 hover 动画改的是 `box-shadow`，鼠标扫过时整张卡片都在重绘；
- 列表项里有一个“阅读进度”的小圆环，用 JS 在 scroll 事件里读 `getBoundingClientRect()` 再改 `style`。

改法分别是：毛玻璃保留但给导航单独分层并限制高度；hover 阴影改成用一个伪元素预先画好阴影，hover 时只改伪元素的 `opacity`；进度圆环改用 `IntersectionObserver`，不再在 scroll 里读布局。改完之后滚动帧率稳定在 60，主线程每帧的渲染时间从 11ms 降到不到 3ms。

理解这条管线最大的收获，不是记住一堆术语，而是以后再遇到卡顿时，能很快判断“这是布局的问题、绘制的问题，还是 JS 的问题”，然后直接去 Performance 面板里对着颜色找证据，而不是凭感觉乱改。
